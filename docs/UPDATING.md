# Update your studio

Open an editing chat from the studio folder. Ask your assistant to update AI Video Studio while preserving projects, media, references, settings and saved feedback. The Updates page has a ready-to-copy request and links to the official repository and releases: https://github.com/mattp68/ai-video-studio . Checking releases is separate from installing an update.

## Assistant update procedure

1. Read AGENTS.md, current STATUS/PROJECT_CONTEXT and capability guidance. Identify this exact installation and its source version. The interface build is recorded in the studio-version meta tag in style-library/dist/index.html; package.json records official release versions. A +ux suffix denotes a local preview, not a separately published release. Do not confuse the maintainer's private production workspace with the separate public starter.
2. Inspect Git status/remotes and official releases at https://github.com/mattp68/ai-video-studio/releases before changing source. Explain the available version and meaningful changes; never report latest without checking. Include prereleases for beta installations: GitHub's releases/latest endpoint omits them. Select a numbered published release/tag, not an arbitrary main/dependency branch, and verify its source manifest. Read that release's update guide before applying it. Keep newer local improvements; do not downgrade a preview based only on its beta prefix.
3. Make a recoverable source checkpoint and fingerprint owner data. Preserve projects/ (including script-state.json), raw/source media, exports, catalogs (including removed_references), techniques, settings, approval decisions, saved feedback, style-library/reference-notes.json and review-feedback-links.json, journals and local customizations. Never use git reset --hard, git clean, seed replacement or a wholesale folder replacement to force an update. Do not publish, push or change accounts/permissions while updating.
4. For a clean official Git checkout, fast-forward to the reviewed release when possible. A template/fork may have its own origin; verify the official source rather than changing the user's remote by assumption. Reconcile local source changes instead of overwriting them; ask for input only for unresolved conflicting choices. For a ZIP installation, use the new release's explicit source allowlist/manifest to replace reviewed code/docs only. Compare installed source with the baseline release to detect local modifications before replacement. If the baseline is unknown, retain conflicting files and ask about unresolved differences. New files must not collide with owner files or symlinks. Delete an obsolete source only when the prior manifest proves it was application source and it is unchanged locally; never delete by folder glob. Do not replace the whole folder, unpack blindly over it, or copy .example.json over existing registries. For a private production workspace, port reviewed reusable changes explicitly; do not turn it into the public checkout.
5. Read dependency/setup changes before running them. Preserve the existing capability mode: studio-only users need no new media packages. Re-running the standard setup creates seeds only when missing; verify that contract for the selected release. An update never grants optional account access. Obtain any genuinely new paid/system authorization separately.
6. Run the release's relevant tests and registry checks. Use disposable fixtures for writes, approvals and saves. Restart only this installation's verified server process, discovered through runtime/server.json and its health/root response; leave other preview processes running. Inspect current projects/references read-only and confirm all owner fingerprints match. Do not render or approve a real project as an update test.
7. Report the installed version, changes, verification and any remaining limits. Keep the previous source checkpoint for rollback; restore affected code only and retain any owner data created since it. Updating the app does not update or publish a creative deliverable.

## Release maintenance

Beta.1 → beta.2 adds source files and optional owner records; existing catalog schema4/projects schema1 records remain compatible and no destructive data migration is required. Missing feedback/script/reference-note files are created only by their explicit save actions. Existing techniques, source IDs/ranges/hashes, removed markers and owner media must remain intact. Retain backup and fingerprint evidence until the user has verified their real workflow.

The beta.1 release predates this guide and the Updates UI. Paste this directly into a chat opened in that existing studio folder:

> Update this existing AI Video Studio from https://github.com/mattp68/ai-video-studio/releases to the newest appropriate published release, including betas. Read docs/UPDATING.md from that release first. Back up this installation and preserve my projects, videos, reference library, techniques, scripts, settings, feedback and local customizations. Never replace my populated library with empty starter files. Verify the update and report the installed version and anything that needs my input.

Before tagging a future release, update the studio-version meta tag and the Updates page's preview description/status for the actual build. Keep docs/VALIDATION.md and release notes accurate. Include this guide in the source allowlist. The installed version describes the files shipped in this copy; no background network check or automatic installer is required.

Editor working copies are retained and reopened for the same project/artifact and unchanged original source revision. Manual changes in that copy are never replaced on reopen. A changed original source prepares a new copy and keeps earlier ones. The owner-only session pointer is in style-library/runtime/editor-sessions/; the full copy stays under its project. Generated render/history caches are not required to carry source into the new editor session.


Feedback corrections (pending release) add optional history, updated_at and deleted_at fields to existing schema1 notes, plus content revisions on newly copied selections. No owner-data rewrite or seed replacement is required. Preserve these fields and all note/link records during upgrade and rollback; old app versions do not understand deletion markers, so do not use their feedback-copy UI after creating corrected/deleted notes. Roll back source only while retaining the newer data, and use a compatible assistant/read path for those notes.
