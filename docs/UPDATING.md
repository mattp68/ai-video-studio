# Update your studio

Open an editing chat from the studio folder. Ask your assistant to update AI Video Studio while preserving projects, media, references, settings and saved feedback. The Updates page has a ready-to-copy request and links to the official repository and releases: https://github.com/mattp68/ai-video-studio . Checking releases is separate from installing an update.

Blender is an optional local capability. The update adds detection and editing guidance. If Blender is already installed, `python3 scripts/setup.py --check` reports its version and `python3 scripts/blender_smoke.py` verifies a disposable render. The normal setup and update workflow works without it.

## Existing installations with media tooling

The copied Updates request is an assistant handoff, not an automatic installer. In the existing studio, read this release's guide, compare/checkpoint its source and preserve its owner data, then update the reviewed application files and both package files together. A studio-only installation remains studio-only. For a media installation, verify Node >=22.12.0, then use the updated scripts/setup.py for the pinned media dependencies and render browser; keep --transcription only where the owner already uses it. Never use an unpinned HyperFrames upgrade or npm audit fix --force. Custom installations without the standard setup script must follow the same preview-inventory and source-checkpoint rules before any manual package commands.

Before any dependency replacement, inventory this installation's running HyperFrames previews using its existing local CLI: preview --list --json. Match projectDir against this studio's resolved root; previews from other installations are outside this update. Updated full setup performs this check and refuses to install when an owned preview is running or its inventory cannot be verified. If it stops, preserve the dependency tree and staged source, explain the pause, and let the owner save/close affected previews or explicitly authorize an isolated continuation. Do not kill other work, bypass the check blindly, or report the new renderer installed while it is only staged.

Checkpoint authored composition/source files as well as application files before changing the renderer: HTML, CSS, JavaScript, project JSON, editor working copies and relevant history/source metadata. Fingerprints detect a change; they do not provide restoration bytes. Retain the originals in an owner-only backup outside published source. Never restart or open an accepted original composition merely to test the upgrade: a HyperFrames preview can automatically stamp IDs and normalize HTML on startup. Use a separate disposable fixture for tests; when the owner wants to resume editing, preserve the original and open an isolated working copy through the Studio handoff. Keep previous renderer source/lock checkpoints and later owner work for rollback.

After installation, verify the actual local CLI version against package.json, run a disposable synthetic check/render and both real registry validators, then restart only the exact Studio server. Confirm owner source/media/records against the checkpoint, separately identifying regenerated runtime caches. The app update does not re-render or approve a creative deliverable. A safe pause for an active editor is preferable to replacing its dependencies underneath it.

## Assistant update procedure

1. Read AGENTS.md, current STATUS/PROJECT_CONTEXT and capability guidance. Identify this exact installation and its source version. The interface build is recorded in the studio-version meta tag in style-library/dist/index.html; package.json records official release versions. A build suffix such as +ux or +feedback denotes a local preview, not a separately published release. Do not confuse the maintainer's private production workspace with the separate public starter.
2. Inspect Git status/remotes and official releases at https://github.com/mattp68/ai-video-studio/releases before changing source. Explain the available version and meaningful changes; never report latest without checking. Include prereleases for beta installations: GitHub's releases/latest endpoint omits them. Determine the newest published release from published_at and numeric version tags; do not assume the first API list entry is newest or sort beta suffixes as plain strings. Select a numbered published release/tag, not an arbitrary main/dependency branch, and verify its source manifest. Read that release's update guide before applying it. Keep newer local improvements; do not downgrade a preview based only on its beta prefix. Run `python3 scripts/check_install.py` to compare the installed application files with the installed version's published manifest (if this installation predates the script, run it from the selected release with `--root` pointing here). Modified files are local customizations or older copies to reconcile; missing files belong to that release.
3. Make a recoverable source checkpoint and fingerprint owner data. Preserve projects/ (including script-state.json, script-brief.json, script-hooks.json and script-feedback.json), raw/source media, exports, catalogs (including removed_references), techniques, settings, style-library/writing-voice.json, approval decisions, saved feedback, style-library/reference-notes.json and review-feedback-links.json, journals and local customizations. Never use git reset --hard, git clean, seed replacement or a wholesale folder replacement to force an update. Do not publish, push or change accounts/permissions while updating.
4. For a clean official Git checkout, fast-forward to the reviewed release when possible. A template/fork may have its own origin; verify the official source rather than changing the user's remote by assumption. Reconcile local source changes instead of overwriting them; ask for input only for unresolved conflicting choices. For a ZIP installation, use the new release's explicit source allowlist/manifest to replace reviewed code/docs only. Compare installed source with the baseline release to detect local modifications before replacement. If the baseline is unknown, retain conflicting files and ask about unresolved differences. New files must not collide with owner files or symlinks. Delete an obsolete source only when the prior manifest proves it was application source and it is unchanged locally; never delete by folder glob. Do not replace the whole folder, unpack blindly over it, or copy .example.json over existing registries. For a private production workspace, port reviewed reusable changes explicitly; do not turn it into the public checkout.
5. Read dependency/setup changes before running them. Preserve the existing capability mode: studio-only users need no new media packages. Re-running the standard setup creates seeds only when missing; verify that contract for the selected release. An update never grants optional account access. Obtain any genuinely new paid/system authorization separately.
6. Run the release's relevant tests and registry checks. Before restarting the studio, run `python3 style-library/library.py validate` and `python3 style-library/project_index.py validate` with the new code against the owner's actual registries. Both must pass, including the check that every registered library file can still be served. If a file would stop being served, stop: never move, rename or re-register owner media to fit a release layout. Reconcile the installation, or ask, and record any local adaptation so the next update keeps it. Use disposable fixtures for writes, approvals and saves. Restart only this installation's verified server process, discovered through runtime/server.json and its health/root response; leave other preview processes running. Inspect current projects/references read-only and confirm all owner fingerprints match. Do not render or approve a real project as an update test.
7. Report the installed version, changes, verification and any remaining limits. Keep the previous source checkpoint for rollback; restore affected code only and retain any owner data created since it. Updating the app does not update or publish a creative deliverable.

## Release maintenance

Beta.1 → beta.2 adds source files and optional owner records; existing catalog schema4/projects schema1 records remain compatible and no destructive data migration is required. Missing feedback/script/reference-note files are created only by their explicit save actions. Existing techniques, source IDs/ranges/hashes, removed markers and owner media must remain intact. Retain backup and fingerprint evidence until the user has verified their real workflow.

The beta.1 release predates this guide and the Updates UI. Paste this directly into a chat opened in that existing studio folder:

> Update this existing AI Video Studio from https://github.com/mattp68/ai-video-studio/releases to the newest appropriate published release, including betas. Read docs/UPDATING.md from that release first. Back up this installation and preserve my projects, videos, reference library, techniques, scripts, settings, feedback and local customizations. Never replace my populated library with empty starter files. Verify the update and report the installed version and anything that needs my input.

Before tagging a future release, update the studio-version meta tag and the Updates page's preview description/status for the actual build. Keep docs/VALIDATION.md and release notes accurate. Include this guide in the source allowlist. The installed version describes the files shipped in this copy; no background network check or automatic installer is required.

Editor working copies are retained and reopened for the same project/artifact and unchanged original source revision. Manual changes in that copy are never replaced on reopen. A changed original source prepares a new copy and keeps earlier ones. The owner-only session pointer is in style-library/runtime/editor-sessions/; the full copy stays under its project. Generated render/history caches are not required to carry source into the new editor session.


Beta.2 → beta.3 feedback corrections add optional history, updated_at and deleted_at fields to existing schema1 notes, plus content revisions on newly copied selections. No owner-data rewrite or seed replacement is required. Preserve these fields and all note/link records during upgrade and rollback; old app versions do not understand deletion markers, so do not use their feedback-copy UI after creating corrected/deleted notes. Roll back source only while retaining the newer data, and use a compatible assistant/read path for those notes.

Beta.3 → beta.4 changes documentation, the studio.config.json sound-default wording and the maintainer release check only. There is no application code, dependency, renderer or owner-data change. If the installed studio.config.json differs from the beta.3 baseline, treat it as a local customization and keep it.

Beta.4 → beta.5 adds scripts/check_install.py, a served-file check in library validation and updated Updates-page wording. There is no dependency, renderer or owner-data change. If validation now reports a registered file that would not be served, that item already could not play in the studio: reconcile its registration or the installation's confinement rules rather than moving owner media.

Beta.5 → beta.6 changes scripts/register.py so a newly registered project is inserted first in projects.json; --replace keeps a record's position and reference registrations still append. There is no interface, dependency, renderer or owner-data change, and existing projects.json order is not rewritten during the update.


### Beta.6 → beta.7 — optional script writing

The optional scripting feature adds shared writing guidance, an optional Script section, per-project script-brief.json and local style-library/writing-voice.json. Both owner records start absent/empty and are created only by a save. Setup must never seed over them. Preserve their complete histories with script-state.json when upgrading or rolling back source. Writing memory is private; it is not a template to copy from the maintainer.

Optional script openings and copied revision feedback add project-local script-hooks.json and script-feedback.json only when explicitly saved/copied. They start absent; preserve all versions, request IDs and content revisions on upgrades/rollback. Older code does not display these records but must not remove them.


Writing memory adds optional examples and forgotten_at fields to existing entries in style-library/writing-voice.json. Legacy entries keep their IDs, text, source and complete version history. Fresh installations start empty. Forget retains a record for explicit Undo while excluding it from active recall. Preserve these optional fields on updates. Rollback to a version predating these fields requires memory-compatible helpers to read enriched records. Keep the newer owner data intact.


### Beta.7 → beta.8 — library dates and approval links

This source-only fix adds automatic dates and exact linking to registration, plus guarded recovery of a missing link during final approval. No catalog rewrite or date migration runs during setup/update. Existing created_at/added_at/added_on values, undated records, reference IDs, removed markers, technique snapshots, approvals, histories and media are retained. Backfill an old date only from reliable saved evidence, retaining its known precision. Approval time is not an added date. New registration journals use the existing recoverable transaction format. Source rollback retains all owner data and newly saved links/dates.

## Beta.8 → beta.9 renderer update

Media installations move from HyperFrames 0.8.144 to 0.9.16 with the scoped Undici 7.30.2 security override; package.json and package-lock.json must be updated together. Before installing, verify Node >=22.12.0. Keep GSAP, Python locks, owner data, saved compositions and all existing editor working copies. Run the release's normal full setup for existing media capability (including --transcription only where already used), or npm ci --ignore-scripts plus the pinned CLI's browser ensure when the existing Python tooling is retained. No global tool, skill or account update is required. A --studio-only installation remains --studio-only and needs no renderer download.

Verify new rendering only in disposable fixtures, then validate the real registries before restarting the exact studio. Existing exported videos are unchanged. For rollback, restore both prior package files and reviewed source, then npm ci --ignore-scripts and the old pinned browser ensure for a media installation; keep all owner records and newer creative work. Do not erase caches/history or reinitialize projects. Owners with custom distributed cloud stacks must follow the upstream 0.9 Plan-v2 migration separately; ordinary local rendering does not deploy or depend on those services.

### Beta.11 → beta.12 — reference techniques
